# Project Deep Refactor Design

## 目标

在不改变现有业务语义和主要页面路由的前提下，对当前 `Vue 3 + Vite + Electron` 项目做一次深度重构，解决导航配置分散、超大文件膨胀、工程检查噪音过高、模块边界不清的问题，让项目从“功能集合”演进为“可持续迭代的桌面应用骨架”。

## 现状判断

当前项目可以正常通过 `pnpm type-check`，但仍有几类明显的结构性问题：

- `src/router/index.ts` 同时承担路由注册、业务分组表达、导航语义承载，已经偏重。
- `src/components/sideMenu.vue` 同时承担菜单配置、激活匹配、展开逻辑和视觉实现，重复承载了大量路由信息。
- 多个页面文件体积过大，尤其是 `src/views/campus-3d/index.vue`、`src/views/im/index.vue`、`src/views/file-upload/index.vue` 等，已经不利于继续演进。
- `pnpm lint` 被 `src/vendor/vue-office-docx` 这类第三方 vendor 文件大量干扰，导致工程检查结果失去参考价值。
- 导航、路由、页面模块之间缺少单一事实来源，维护时容易出现“菜单变了但路由没同步”或“页面迁移了但导航匹配规则遗留”的问题。

## 重构范围

本次重构覆盖以下内容：

- 建立统一的模块导航配置源，收拢侧边菜单和路由元数据中的重复信息。
- 拆分 `sideMenu` 与 `router` 中的职责，让它们分别退回到“展示层”和“挂载层”。
- 选取 1 到 2 个最值得处理的大文件页面，按“页面编排 + composable + 子组件/数据文件”方式拆分。
- 调整 ESLint 配置或忽略范围，使 vendor 代码不再污染主工程检查。
- 补上与导航配置、拆分结果匹配的静态验证或脚本验证。

## 不在本次范围内

以下内容明确不做：

- 不更换技术栈，不从 Element Plus 迁移，不改用其他状态管理方案。
- 不修改现有页面 URL 语义，除非仅增加兼容跳转。
- 不整体重写所有大页面，只优先处理收益最高的样本模块。
- 不重写 Electron 主进程结构。
- 不引入新的设计系统或全面视觉翻新。

## 设计方案

### 1. 导航与路由配置收口

新增独立模块配置文件，作为“导航语义单一事实来源”。该配置至少承载以下信息：

- 模块分组 key、标题、图标、默认展开状态；
- 子项路径、显示标题、描述、图标、主题色、激活匹配规则；
- 是否出现在侧边导航；
- 与路由 `meta.title` 对应的显示文案。

`src/components/sideMenu.vue` 不再直接内嵌完整菜单结构，而是消费模块配置并只保留：

- 折叠/展开状态；
- 当前路由激活判断；
- 菜单渲染。

`src/router/index.ts` 只保留页面注册和必要重定向。对于适合从模块配置派生的部分，抽出路由记录工厂或路由片段，避免单文件继续增长。

### 2. 大文件拆分策略

本次优先处理两个层次：

- 必拆：`src/components/sideMenu.vue`、`src/router/index.ts`
- 样本页拆分：优先从 `src/views/im/index.vue` 或当前正在整理的业务中台相关页面中选择一个稳定页面作为模式样本

拆分原则如下：

- 静态数据进 `data.ts` 或 `config.ts`
- 交互状态进 `useXxx.ts`
- 页面只负责组合子组件和页面级编排
- 复杂局部区域拆成同目录 `components/`

对于 `campus-3d` 这类体量极大且可能包含连续场景逻辑的页面，本轮只做可拆边界评估，不把它作为第一优先实施对象，避免高风险改动吞掉本轮节奏。

### 3. 工程检查恢复

调整 ESLint 范围，让第三方 vendor 文件不再纳入主工程规则校验。原则是：

- 业务源码必须继续受 lint 约束；
- vendor 文件可以通过忽略规则隔离，而不是为整个项目放松规范；
- 保持 `pnpm type-check` 与 `pnpm lint` 都能作为有效信号。

如果当前已有脚本测试依赖 `sideMenu.vue` 的静态结构，则同步把测试改为面向新的配置文件或新的渲染输出，避免测试和实现强耦合。

### 4. 体验一致性整理

在不改变核心业务行为的前提下，顺手统一以下体验问题：

- 侧边导航分组命名、激活态、默认展开逻辑；
- 导航入口的文案和描述风格；
- 重复或分散入口的归类方式；
- 页面内可抽离的局部信息区块，减少单页既管数据又管视觉的混合写法。

这部分属于“伴随式优化”，只在重构触达的模块内进行，不做全项目视觉重绘。

## 文件边界设计

预计新增或调整的重点文件边界如下：

- `src/config/navigation.ts`
  负责模块导航配置、菜单分组和导航项元数据。
- `src/router/modules/*.ts` 或类似结构
  负责按业务域拆分路由记录，再在主路由文件汇总。
- `src/components/sidebar/*`
  负责侧边导航的展示组件、类型和局部工具函数。
- `src/views/<module>/components/*`
  负责拆分后的页面局部区域。
- `src/views/<module>/use<Module>.ts`
  负责页面状态和交互逻辑。

如果现有目录已经有更适合的本地模式，则以项目现状为准，不为拆分而制造额外层级。

## 数据流与依赖关系

重构后的依赖方向应保持简单：

- 页面视图依赖 composable、子组件、服务层。
- 侧边菜单依赖统一导航配置和当前路由信息。
- 路由注册依赖路由片段或路由配置，不反向依赖菜单组件。
- 服务层继续维持现有 API 包装角色，不在本轮引入新的跨层抽象。

这样可以确保导航调整、页面拆分和业务服务变化彼此解耦，不再需要在多个大文件中同步修改同一份语义。

## 风险与控制

主要风险有三类：

- 菜单和路由收拢时，激活匹配规则可能出现回归。
- 页面拆分后，局部响应式状态或事件传递可能遗漏。
- 工作区当前已有未提交改动，若直接改动相同文件，可能与既有修改冲突。

控制方式：

- 先把配置提炼出来，再迁移菜单消费，最后清理旧结构。
- 优先改动新增文件或局部提取，减少覆盖式重写。
- 在动到 `sideMenu.vue`、`router/index.ts` 等现有热区前，先完整阅读并兼容已有未提交改动。
- 每完成一个重构面，立即运行对应验证命令。

## 测试与验证

本次重构至少需要以下验证：

- `pnpm type-check`
- `pnpm lint`
- 与导航结构有关的脚本测试
- 与被拆页面有关的脚本测试或最小可运行验证

如果现有脚本测试不足以覆盖导航配置迁移，则新增轻量脚本测试，校验：

- 模块配置中关键分组和入口存在；
- 路由中关键页面仍可访问；
- 菜单默认展开配置与目标分组一致；
- 历史兼容跳转仍保留。

## 实施顺序

建议按以下顺序落地：

1. 恢复工程检查可用性，先解决 vendor lint 噪音。
2. 提炼统一导航配置与相关类型。
3. 重构侧边菜单为数据驱动渲染。
4. 拆分路由定义，压缩主路由文件复杂度。
5. 选取一个高收益页面完成样本级拆分。
6. 补齐测试并跑通验证。

## 成功标准

完成后应满足以下结果：

- `pnpm lint` 与 `pnpm type-check` 都能稳定运行并对主工程提供有效反馈。
- 菜单配置不再直接硬编码在 `sideMenu.vue` 中。
- 主路由文件明显缩短，业务分组更清晰。
- 至少一个典型大页面完成可复用的拆分模式。
- 用户可见路由、主入口和核心业务行为保持不变。
