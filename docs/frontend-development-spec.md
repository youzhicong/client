# 前端开发工程师规范

## 1. 适用范围

本规范适用于当前项目的 `Vue 3 + TypeScript + Vite + Element Plus + Pinia` 技术栈，用于统一目录结构、页面拆分、公共能力沉淀、插件选型、编码风格、联调方式、提交流程和验收标准。

本规范不是建议项，而是默认开发标准。新功能开发、旧页面重构、公共能力抽离、代码评审都必须以本规范为准。

---

## 2. 核心目标

- 保证页面结构清晰，模块边界明确
- 保证组件职责单一，逻辑可复用、可维护
- 优先复用成熟方案，避免重复造轮子
- 保证项目结构符合主流前端工程标准
- 降低后续维护成本、交接成本和重构成本

---

## 3. 红线规则

以下规则为强制要求：

1. 每个模块页面的功能必须拆分为独立组件，放在该模块目录下，不允许把完整业务堆在一个 `index.vue` 中。
2. 市面上存在成熟组件库时，必须优先使用成熟组件，不允许重复实现基础组件。
3. 多模块共用的功能、组件、方法、样式变量，必须抽到公共层，不允许复制粘贴多份。
4. 市面上存在成熟插件时，必须优先评估插件方案；只有插件无法满足需求时，才允许自行开发。
5. 图片、图标、状态图、菜单图标等能使用 `SVG` 的场景必须优先使用 `SVG`，并统一组件化。
6. 请求封装、请求拦截器、响应拦截器、状态管理、持久化能力必须标准化，符合主流前端工程结构。
7. 环境变量、路由、权限、全局设置、主题配置等必须独立维护，不允许散落在业务组件中。
8. 父组件尽量只做展示和编排；局部数据请求、局部状态、局部业务逻辑优先下沉到子组件或 `hooks`。
9. 禁止一个文件同时承担页面展示、接口请求、复杂计算、表单校验、弹窗逻辑、表格逻辑和样式体系。
10. 禁止为赶进度直接在页面里临时写死大量 mock 数据、权限判断、请求逻辑和重复方法。

---

## 4. 目录规范

推荐 `src` 目录结构如下：

```text
src/
  assets/                 静态资源
  components/             公共组件
  composables/            通用 hooks / 组合式逻辑
  constants/              全局常量
  enums/                  全局枚举
  icons/                  SVG 图标资源
  layout/                 布局组件
  router/                 路由配置
  services/               接口层
  stores/                 状态管理
  style/                  全局样式、主题、变量
  types/                  全局类型
  utils/                  工具函数
  vendor/                 三方封装或特殊适配
  views/                  业务页面
  permission.ts           路由权限控制
  main.ts                 应用入口
```

单个业务模块目录结构如下：

```text
src/views/module-name/
  index.vue               页面入口，只做编排
  components/             模块私有组件
  hooks/                  模块私有 hooks（可选）
  types.ts                模块类型
  constants.ts            模块常量（可选）
  enums.ts                模块枚举（可选）
  utils.ts                模块内部工具（可选）
  xxxData.ts              静态配置或演示数据（可选）
  useXxx.ts               模块逻辑 hook
```

### 4.1 目录边界

- `src/components/` 只放跨模块复用组件
- `src/views/xxx/components/` 只放当前模块私有组件
- `src/composables/` 只放跨模块复用的组合逻辑
- `src/enums/` 只放跨模块复用的枚举定义
- `src/services/` 只放接口调用，不写页面逻辑
- `src/stores/modules/` 只放全局或跨组件共享状态
- `src/utils/` 只放纯函数或浏览器能力封装

### 4.2 公共层抽离标准

满足以下任意条件，应抽到公共层：

- 被两个及以上业务模块复用
- 后续明确会重复出现
- 逻辑复杂且通用性强
- 样式和交互有统一标准

## 5. 页面与组件拆分规范

### 5.1 页面入口必须薄

`index.vue` 的职责仅限于：

- 组织页面布局
- 组合模块组件
- 处理页面级路由参数
- 处理模块级协调逻辑

`index.vue` 不允许直接承载：

- 大段业务模板
- 大量接口请求
- 复杂表单逻辑
- 复杂表格逻辑
- 多个弹窗状态
- 大量样式定义

### 5.2 页面标准拆分方式

一个复杂页面至少按功能区拆分，例如：

- `PageHero.vue`
- `FilterPanel.vue`
- `StatsRow.vue`
- `TableCard.vue`
- `EditDialog.vue`
- `DetailDrawer.vue`
- `Workspace.vue`

### 5.3 父子组件职责

父组件原则上只做页面结构编排和少量状态协调：

- 父组件尽量只做展示
- 局部请求优先放子组件
- 局部逻辑优先放子组件或 `useXxx`
- 父组件只有在必须统一调度多个子组件数据时，才保留请求逻辑

子组件应尽量做到：

- 自己请求本区块数据
- 自己维护本区块的 loading / empty / error 状态
- 自己处理局部交互逻辑
- 只通过明确的 `props` / `emit` 与父组件通信

### 5.4 组件拆分触发条件

出现以下情况必须拆分：

- 单文件超过 300 行仍在持续增长
- 模板中出现多个功能区块
- 一个组件中有多个弹窗或抽屉
- 一个组件中有多个表格或多个表单
- 同一逻辑可在多个地方复用
- 模板中出现复杂计算表达式

### 5.5 组件设计要求

- `props` 必须显式声明类型
- `emit` 必须显式声明事件类型
- 组件名必须表达业务语义
- 不允许出现 `test.vue`、`demo.vue`、`new.vue`、`temp.vue`
- 组件默认以单一职责为目标，不做“万能大组件”

## 6. hooks / composables 规范

### 6.1 哪些逻辑必须下沉到 hook

以下逻辑优先抽到 `useXxx.ts`：

- 列表查询与分页
- 表单提交与重置
- 弹窗显隐与状态流转
- 上传流程
- 拖拽、图表、播放器、Three.js 场景控制
- 复杂计算和数据格式转换
- 页面级状态流转

### 6.2 hook 设计要求

- 命名统一为 `useXxx`
- 只暴露页面需要的状态和方法
- 避免返回无语义的大对象
- 逻辑按“状态、计算、动作”分组
- 可复用逻辑优先沉到 `src/composables/`

### 6.3 禁止事项

- 禁止在多个页面复制同一段组合式逻辑
- 禁止把纯工具函数塞进 hook
- 禁止 hook 里直接耦合某个页面 DOM 结构，除非该 hook 只服务该模块

## 7. UI 组件与插件使用规范

### 7.1 组件优先级

功能实现优先级如下：

1. 项目已有公共组件
2. 现有组件库能力
3. 成熟第三方插件
4. 对现有组件或插件做二次封装
5. 最后才是自研

### 7.2 优先使用的组件与库

当前项目优先使用：

- `element-plus`
- `@element-plus/icons-vue`
- `echarts`
- `three`
- `axios`
- `pinia`
- `pinia-plugin-persistedstate`
- `vite-plugin-svg-icons`
- `nprogress`

### 7.3 插件选型标准

选型时至少评估：

- 是否支持 Vue 3
- 是否支持 TypeScript
- 社区是否活跃
- 文档是否完整
- 维护成本是否可控
- 包体积是否合理
- License 是否安全

### 7.4 不允许重复造轮子的场景

以下场景优先插件或组件库：

- 日期时间处理
- 富文本
- 图表
- 流程图
- 文件预览
- 上传
- 二维码 / 条码
- 视频播放
- 表格
- 树结构
- 3D 展示
- 拖拽排序

## 8. SVG、图片与资源规范

### 8.1 图标规范

- 能用 `SVG` 就不用位图
- `SVG` 统一通过插件接入
- `SVG` 必须封装成组件使用
- 不允许在业务代码中到处手写零散 `svg` 片段

### 8.2 资源使用规范

- 图标优先 `SVG`
- 内容图优先 `webp`
- 大图必须压缩
- 禁止提交无优化的大资源
- 禁止把图片散落到各模块随意引用

### 8.3 统一图标组件

项目图标必须优先通过统一图标组件使用，例如：

## 9. 接口、请求与数据层规范

### 9.1 请求必须统一管理

所有接口请求必须放在 `src/services/`：

- 页面和组件中禁止直接写 `axios`
- 服务层只处理接口调用和数据入参
- 服务层不处理页面提示文案和业务 UI 状态

### 9.2 请求封装标准

统一请求封装必须处理：

- `baseURL`
- token 注入
- 超时设置
- 请求头
- 统一错误处理
- 登录失效处理
- 响应解包
- 可选的重复请求控制

当前项目统一请求入口：

- [request.ts](C:/Users/c/Desktop/自研vue3/vue-pcdemo/src/utils/request.ts)

### 9.3 API 类型要求

- 接口入参和出参必须定义类型
- 接口返回结构必须统一建模
- 不允许页面里临时断言一大片 `as any`
- 不允许不同页面对同一接口返回值各写一套类型

### 9.4 数据转换边界

数据转换职责划分如下：

- 服务层：负责接口入参与原始响应
- hook 层：负责页面使用前的数据整理
- 组件层：只消费最终可展示数据

## 10. 状态管理规范

### 10.1 使用范围

`Pinia` 只用于以下场景：

- 用户信息
- 登录状态
- 跨页面共享状态
- 多组件共享状态
- 需要持久化保存的状态

### 10.2 不应滥用 store

以下内容不要放入全局 store：

- 当前页面局部弹窗显隐
- 当前组件输入框内容
- 只在一个页面里使用的短期状态
- 明显属于局部组件内部的 UI 状态

### 10.3 持久化规范

需要持久化的状态，统一使用：

- `pinia-plugin-persistedstate`
- 或明确封装后的浏览器存储工具

禁止在业务页面中随意零散读写 `localStorage` / `sessionStorage`。

## 11. 路由、权限与环境变量规范

### 11.1 路由规范

- 路由统一维护在 `src/router/`
- 页面元信息统一通过 `meta` 管理
- 不允许把路由逻辑散落到页面组件中

### 11.2 权限规范

- 登录态校验、路由守卫、权限判断统一放在权限层
- 页面只关心“是否可见”“是否可操作”，不重复实现守卫逻辑
- 按钮级权限应封装成指令、函数或统一判断工具

当前项目权限入口：

- [permission.ts](C:/Users/c/Desktop/自研vue3/vue-pcdemo/src/permission.ts)

### 11.3 环境变量规范

- 不同环境必须使用独立 `.env` 文件
- 环境变量命名统一前缀
- 环境差异不允许硬编码在业务文件中
- API 地址、开关配置、构建模式必须走环境变量

### 11.4 配置集中管理

以下配置必须单独维护：

- 环境变量
- 路由配置
- 权限配置
- 全局设置
- 主题变量
- 常量枚举

## 12. 类型、常量与命名规范

### 12.1 类型规范

- 核心业务数据必须先定义类型再开发
- `props`、表单模型、表格行、接口响应必须有类型
- 除框架兼容场景外，禁止大面积使用 `any`
- 优先使用 `type` / `interface` 表达清晰语义

### 12.2 常量规范

以下内容优先抽常量：

- 枚举值
- 路由名
- 状态文案
- 表格列配置
- 筛选项配置
- 默认表单值

### 12.3 枚举规范

- 跨模块复用的枚举统一放在 `src/enums/`
- 仅模块内部使用的枚举放在当前模块的 `enums.ts`
- 枚举命名必须表达业务语义，例如 `UserStatusEnum`、`ApprovalNodeTypeEnum`
- 枚举值必须稳定，禁止同一业务含义在不同文件重复定义多套值
- 如果接口返回值本身就是固定枚举语义，前端必须建立对应枚举或联合类型，不允许到处手写字符串

### 12.4 命名规范

- 组件文件：`PascalCase.vue`
- 页面目录：`kebab-case`
- hook 文件：`useXxx.ts`
- 类型文件：`types.ts`
- 常量文件：`constants.ts`
- 枚举文件：`enums.ts`
- 数据配置文件：`xxxData.ts`

命名必须表达业务含义，不允许无语义命名。

## 13. 样式规范

### 13.1 样式层级

- 页面私有样式跟随页面组件
- 模块私有样式跟随模块组件
- 组件私有样式必须跟随组件文件维护，优先与组件同文件放置
- 父组件只保留自身布局样式，不承载子组件的大量私有样式
- 全局样式、主题变量、reset 统一放在 `src/style/`

### 13.2 样式要求

- 颜色、字号、间距优先提取变量
- 避免层级过深
- 避免全局污染
- 避免一个页面定义大量重复样式块
- 样式命名应与业务结构对应
- 禁止因为拆分组件，就把所有样式集中抽到一个公共样式文件
- 只被单个组件使用的样式，不允许提前抽到模块公共层
- 公共样式抽离必须以“真实复用”为前提，不能为了看起来整齐而集中存放

### 13.3 样式归属与抽离边界

- 组件内部结构、状态、交互相关样式，必须放在当前组件内
- 页面级容器布局、区块编排样式，可以放在页面入口组件
- 仅当两个及以上组件稳定复用同一套样式语义时，才允许抽到模块公共层
- 仅当跨模块复用时，才允许继续上提到 `src/style/` 或全局公共层
- `scoped`、CSS Module、组件同级样式文件都可以使用，但归属必须清晰
- 如必须使用 `:deep` 覆盖子组件样式，父组件内只允许保留必要覆盖，不允许顺带托管整块子组件样式
- 禁止出现“组件拆开了，但样式全集中在一个 `xxx.scss` 里”的情况
- 样式抽离后如果反而增加理解成本、跳转成本和维护成本，应回收至对应组件

### 13.4 主题与设计令牌

如项目后续存在统一视觉体系，必须沉淀：

- 主色
- 辅助色
- 边框色
- 字体层级
- 圆角体系
- 阴影体系
- 间距体系

---

## 14. 表单、表格与交互状态规范

### 14.1 表单规范

- 表单模型必须有明确类型
- 校验规则必须可复用时抽离
- 新增 / 编辑尽量复用同一表单组件
- 表单提交必须有 loading 状态
- 表单重置必须恢复到明确初始值

### 14.2 表格规范

- 表格列配置可配置化时优先抽离
- 查询、分页、排序逻辑优先放 hook
- 空状态、loading、异常状态必须统一处理
- 操作按钮权限和禁用态必须明确

### 14.3 统一交互状态

所有页面都必须考虑：

- loading
- empty
- error
- submitting
- disabled
- no-permission

不允许只实现“正常成功态”。

---

## 15. 异常处理规范

### 15.1 统一异常出口

接口异常、权限异常、资源加载失败、表单提交失败必须统一处理，不允许每个页面自由发挥。

### 15.2 提示文案要求

- 提示文案必须明确
- 不要只提示“失败了”
- 要说明失败动作和可能方向
- 对用户可恢复的异常，要提供重试路径

### 15.3 日志要求

- 开发环境允许调试日志
- 提交前清理无意义 `console.log`
- 关键错误应保留必要上下文

---

## 16. 性能规范

### 16.1 必须关注的性能问题

- 大页面拆分
- 大组件拆分
- 重计算缓存与下沉
- 大列表懒渲染
- 大资源压缩
- 非首屏模块按需加载

### 16.2 页面性能要求

- 首屏必要内容优先渲染
- 非必要模块按需加载
- 大图表、大流程图、大 Three.js 场景延迟初始化
- 长列表、长时间轴、超大表格必须评估虚拟化或分页

### 16.3 包体积控制

- 引入第三方库前先评估体积
- 禁止引入同类重复库
- 大功能库优先懒加载

---

## 17. 安全规范

### 17.1 基础安全要求

- 不允许把 token、密钥、敏感地址硬编码到前端代码
- 文件上传前要校验类型、大小、必要格式
- 富文本、外链、文件预览等场景要考虑安全风险
- 不可信 HTML 禁止直接渲染

### 17.2 权限安全

- 前端权限只做体验层控制，不替代后端鉴权
- 任何敏感操作都必须依赖后端校验

---

## 18. 代码质量规范

### 18.1 工程要求

提交前至少保证：

- `pnpm type-check` 通过
- `pnpm lint` 通过
- 关键页面功能自测通过
- 无明显控制台报错

### 18.2 禁止事项

- 禁止大面积 `any`
- 禁止复制粘贴重复逻辑
- 禁止模板内复杂业务计算
- 禁止把 mock 数据长期留在业务页面
- 禁止未封装就直接复用多个相同代码块

### 18.3 文件体量建议

建议控制：

- 页面入口文件尽量小于 80 行
- 单个业务组件尽量小于 300 行
- 超过 500 行必须评估继续拆分
- 超过 800 行默认视为结构异常，必须整改

---

## 19. 测试与验收规范

### 19.1 自测最低要求

每次开发完成至少确认：

- 主流程可用
- 异常提示正常
- 空状态正常
- loading 状态正常
- 移动端或小屏布局不崩
- 刷新页面后状态符合预期

### 19.2 结构整改验收标准

页面整改完成后至少满足：

- 页面入口文件已变薄
- 大段逻辑已沉到 `useXxx`
- 大区块已拆为独立组件
- 公共能力已抽离
- 类型完整
- 类型检查通过

---

## 20. 代码评审规范

评审时重点检查：

- 是否按模块拆分组件
- 是否把逻辑下沉到 hook
- 是否复用已有公共能力
- 是否重复造轮子
- 是否存在明显的父组件过重问题
- 是否滥用 store
- 是否缺失类型
- 是否遗漏 loading / empty / error
- 是否把配置、权限、环境变量写进业务代码
- 是否存在明显可抽离的公共逻辑

不符合规范的代码原则上不应直接合入主分支。

---

## 21. 开发流程规范

### 21.1 新需求处理顺序

收到需求后按以下顺序判断：

1. 项目内是否已有公共能力
2. 组件库是否已有成熟能力
3. 是否有成熟插件可直接接入
4. 是否适合对现有能力做二次封装
5. 最后才是自研

### 21.2 新模块开发顺序

1. 建模块目录
2. 定义 `types.ts`
3. 设计页面拆分方案
4. 新增 `services`
5. 新增 `useXxx.ts`
6. 开发模块组件
7. 接入路由和权限
8. 自测与类型检查

### 21.3 重构顺序

整改旧页面时按以下顺序处理：

1. 先拆入口页
2. 再拆功能区组件
3. 再下沉逻辑到 hook
4. 再抽公共方法和公共组件
5. 最后统一类型和样式

---

## 22. 提交与协作规范

### 22.1 提交前检查

提交前必须确认：

- 无无用文件
- 无无用样式
- 无调试代码
- 无死代码
- 新增目录符合规范

### 22.2 协作要求

- 改公共能力时要评估影响范围
- 改公共类型时要同步检查引用模块
- 改路由、权限、环境配置时要说明影响点
- 结构整改优先保证不改业务行为

---

## 23. 文档规范

以下场景必须补文档或注释：

- 公共组件使用方式
- 公共 hook 使用方式
- 新增插件接入说明
- 特殊业务规则
- 环境变量说明
- 权限规则说明

注释只写必要内容，重点说明：

- 复杂业务规则
- 特殊边界条件
- 兼容性处理原因
- 非直觉实现原因

---

## 24. 最终落地要求

后续所有新增页面、旧页面整改、公共能力建设，都必须满足以下结果：

- 页面入口足够薄
- 模块内部有明确分层
- 父组件不过重
- 逻辑尽量下沉
- 公共能力统一沉淀
- 插件和组件优先复用
- 类型完整
- 结构清晰
- 易维护、易替换、易扩展

如果因特殊场景无法完全遵守，必须在评审时明确说明原因、影响范围和替代方案。
